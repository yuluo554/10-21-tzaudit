## 一、数据清单（三类，各有入仓形态）

> **2026-10-21 定案（Q1）**：金标的"两棵树"一律取 **PyPI `tzdata` wheel（slim 构建）**，版本对齐全、可复现。
> `fat` 构建**不进主金标**，只作 M2 的额外 fixture（从 IANA 源码包自建），用于验证"双引擎合并"的 slim/fat 语义等价。
> 这把 `plan/05` R1（slim/fat 版本对不齐）从主路径移出。

| # | 数据 | 来源 | 入仓形态 | 入仓？ | 产出里程碑 |
|---|---|---|---|---|---|
| D1 | **五份 IANA tzdata 源码包** 2026a–2026e | `https://data.iana.org/time-zones/releases/tzdata<ver>.tar.gz` | 解包后的**必要文本**：`NEWS`、`leap-seconds.list`、`version`；**tar.gz 不入仓** | 部分 | M1 |
| D2 | **编译后的 zoneinfo 树**（slim + fat） | **主线：PyPI `tzdata` wheel（slim）**——`2026.1` / `2026.5` 等；**fat 仅作 M2 的额外 fixture**（从 IANA 源码包自建） | **不入仓**（体积大、可由 D1/D2 重建）；只入 `provenance.json`（URL + sha256 + 版本 + kind） | ❌ | M1 |
| D3 | **金标 JSON** `expect.json` | 由 `bench/run.py --regen` 从 D2 计算 | 入仓（只含输入 + 期望） | ✅ | M1/M4 |
| D4 | **fixture 集**（合成字节 + 合成清单） | `data/fixtures/<kind>/gen.py` | 入仓（生成器 + 产物 + expect + README） | ✅ | M2–M5 |
| D5 | 检索/竞品/需求证据 | 已固化在 `plan/01` 与 `data/README.md` §一 | 文本 | ✅ | M0（已完成） |

### 1.1 D2 为什么可以不入仓（且必须写清重建命令）

- 一个 fat zoneinfo 树约 3–4 MB、slim wheel 约 300 KB；五个版本 × 两种构建 = 数 MB 二进制，
  且**无法用文本 diff 审查**。它们完全可由 D1 + 官方 wheel 重建。
- 重建入口：`py -3.12 tools/fetch_tzdb.py --versions 2026a,2026b,2026c,2026d,2026e --out data/_downloads`
  （M1 落地；`data/_downloads/` 已在 `.gitignore`）。
- 因此 **README 必须有一节"前置条件：先跑 fetch"**（题面 §三 第 6 项 + skill 阶段 7"发布包实测"条）：
  干净 clone 后若未跑 fetch，`bench/run.py --check` 会**明确报缺件**（退出码 3，列出缺失版本），
  而不是 0 项静默通过。

### 1.2 provenance 最小字段（每棵入仓/本地树一份）

M1 实际入仓形态（`data/tzdb/<ver>/provenance.json`，实测值见括号）：

```json
{
  "version": "2026e",
  "kind": "slim",
  "source_url": "https://files.pythonhosted.org/packages/.../tzdata-2026.5-py2.py3-none-any.whl",
  "sha256": "<wheel 的 64 hex>",
  "retrieved": "2026-10-21",
  "zones": 598,
  "notes": "slim wheel from PyPI tzdata 2026.5",
  "pypi_version": "2026.5",
  "source_sha256": "<tzdata2026e.tar.gz 的 64 hex>",
  "source_url_iana": "https://data.iana.org/time-zones/releases/tzdata2026e.tar.gz"
}
```

- `zones` 是**实测回填**（不是题面快照数字）；`bench/run.py` 每次复算后比对，不等即报 `provenance.zones` 漂移。
- `sha256` 是**下载包**的 sha256（不是解包树的），用于"同一版本可重建"。
- **`kind` 必须是 `slim`**（K14 / Q1 定案）：主金标的两棵树全取 PyPI wheel，fat 只在 M2 fixture 里。
- 额外两个字段（M1 实测加入）：`source_sha256` / `source_url_iana` 记**同版本的 IANA 源码包**凭据。
  这样一棵被金标引用的树能同时回答"哪个 wheel 编的"与"对应哪份 IANA 源码"，
  而 `sha256` 字段本身仍严格是 wheel 的（不混淆两个来源）。
- `IANA ↔ PyPI` 的版本映射**不靠猜**：wheel 的 `tzdata/__init__.py` 里有 `IANA_VERSION`，
  `fetch_tzdb.py` 读它并断言与请求版本一致（实测 `2026.1..2026.5` ↔ `2026a..2026e` 一一对应）。

## 二、五版本金标的口径

| 金标文件 | 内容 | 生成方式 | 断言 |
|---|---|---|---|
| `data/tzdb/2026a/expect.json` … `2026e` | 每版本：`zones` 数、`parse_errors`（必须 0）、抽样 zone 的转换点数 | `bench/run.py --regen` | 复算一致；`parse_errors == 0` |
| `data/tzdb/2026a/expect-timeline.json` … `2026e` | 每版本：timeline 抽样集（转换点数 / tail 点数 / **候选数 {0,1,2}**） | `bench/run.py --regen --suite timeline` | 复算一致；候选数集合恰为 `{0,1,2}` |
| `data/tzdb/2026a/expect-windows.json` … `2026e` | 每版本：**全量窗口总数**（分母口径）+ 抽样 zone 在抽样年份的**窗口集合** | `bench/run.py --regen --suite windows` | 复算一致；抽样集**必须同时含 `GAP` 与 `OVERLAP`**（缺则拒绝写出） |
| `data/tzdb/pairs/2026a-2026e.json` | `window_changed`（窗口内变化 zone 名单）、`all_history_changed`（全历史不同 zone 名单）、每条的 `class` + `evidence` | `bench/run.py --regen --suite diff` | 名单与 `diff` 输出**集合相等**（不写死条数） |
| `data/tzdb/pairs/2026.1-2026.5.json` | Vancouver 的 `future_rule` + `evidence=tail` | 同上 | `class == "future_rule"` 且 `evidence == "tail"` |

> **M4 落地说明**：`2026.1-2026.5` 与 `2026a-2026e` 是**同一对标**（PyPI 版本号 ↔ IANA 版本号，
> 见 §1.2 的映射纪律），因此**不另建**一份 `pairs/2026.1-2026.5.json`——那会造出两个
> "同一事实"的金标文件，改一处漏一处必漂。Vancouver 的 `future_rule` + `evidence=tail`
> 由 `pairs/2026a-2026e.json` 的 `changes[]` 里那一条承担
> （`tests/test_diff.py::test_vancouver_real_trees_is_future_rule_with_tail_evidence` 断言）。

**真值纪律（逐条可断言）**

1. **只存输入与期望**：`expect.json` 不得出现 `observed_*` / `actual_*` 字段
   （`tests/test_truth_shape.py` 扫全部 `expect.json`，命中即 FAIL）。
2. **期望可由输入独立复算**：`bench/run.py --check` 用**生产实现**复算并与期望比；期望本身由
   `--regen` 生成，而 `--regen` 也走生产实现——因此必须配一条**独立参照实现**（`tests/reference.py`）
   对**抽样 zone**（≥ 20 个，含三种特殊形态）逐条对拍，否则"期望与实现同源"（引擎自证）。
3. **名单不写死条数**：金标里存的是**集合**（zone 名列表），断言用集合相等；
   报告/README 里的"11 个 / 20 个"这类数字**只在末态回填**，不进代码常量。
4. **金标文件名带版本对**：`2026a-2026e.json` 而不是 `latest.json`——避免"金标跟着最新版漂"。

## 三、fixture 生成纪律

目录：`data/fixtures/{tzif,posix,windows,diff,audit}/`，每个含：

```text
gen.py         # 生成器：固定输入 → 产物；--check 模式只比对不写盘
expect.json    # 金标（只含输入 + 期望）
README.md      # 一句话：注入了什么、为什么需要它
<产物文件>      # 二进制/文本，入仓
```

**硬纪律**

1. **禁 `random` / 禁系统时钟 / 禁 `set` 迭代序**：需要"随机"时用自研 splitmix64（固定 seed）；
   产物内**无时间戳**（除金标显式声明的固定 `generated_at` 常量）。
2. **`gen.py --check` 必须两层断言**：① 入仓产物自身形态正确；② 重新生成到临时目录 →
   与入仓件**逐字节**比对。只做 ① 会在生成器被改坏时仍绿。
3. **写盘归一**：`newline="\n"` / `write_bytes` + `\r\n → \n` 归一；`.gitattributes` 对
   **字节即被测对象**的 fixture 标 `-text`（例如 CRLF 样张——本项目暂无，但规则先立）。
4. **部分运行不改全集清单**：`gen.py --only <name>` 绝不改写 `manifest.json`（M2 起有 manifest 时适用）。
5. **每个 fixture 的 `README.md` 必须写"注入了什么缺陷/形态"**，否则金标无从复核。

**必覆盖的六类 fixture（题面 §三 第 4 项）**

| fixture | 注入 | 断言 |
|---|---|---|
| `tzif/slim-vs-fat/` | 同版本两棵树（slim tail-only / fat 显式表） | 语义等价（重叠区间逐转换点） |
| `tzif/negative-dst/` | Dublin 式负 DST（冬季 `is_dst=1`） | `is_dst` 原样保留 |
| `tzif/half-hour/` | Lord_Howe 式 30 分钟偏移 | `offset_sec=37800` |
| `tzif/quarter-hour/` | Chatham 式 +12:45 | `offset_sec=45900` |
| `posix/three-rule-forms/` | `Jn` / `n` / `Mm.w.d` + `/time` | 展开时刻逐条 |
| `windows/wall-clock-windows/` | 整小时 / 30 分钟 / 45 分钟 / 负 DST / 无 DST / **只换缩写**（陷阱） | GAP 与 OVERLAP 的**方向** + 时长 + 偏移逐条；零窗口 zone 确实零窗口 |
| `diff/change-classes/` | **七种形态合在一个 fixture**（原计划的 `diff/vancouver-tail/` 与 `diff/bc-2026b/` 合并进来）：表逐字节相同仅 tail 变 / BC 永久 UTC−7 / 仅缩写变 / 缩写与 tail 同时变 / link 变独立规则 / link 别名集合变空 / 逐字节相同 | `future_rule`+`tail`、`abbreviation_only`+`abbr`、`alias_only`+`link`、零变更不产出记录；**顺序取第一条成立者**（详见该目录 `README.md`） |
| `audit/bc-scenario/` | 同一 UTC 两版本两墙钟 | `VERSION_CHANGED` 两条 UTC 值 |

> **M4 落地说明（2026-10-21）**：`diff/` 只落**一个** fixture 目录 `change-classes/`，
> 而不是原计划的两个（`vancouver-tail/` + `bc-2026b/`）。理由：
> 两组"旧树 / 新树"共享同一套生成器与同一份 `--check` 流程，拆成两个目录会让
> **同一批 `_support.py` 构造逻辑出现两份**，且"四类互斥 + 判定顺序"这类**跨形态**断言
> 本来就需要在**同一对树**上观察。合并后一个 fixture 同时验七条形态，
> 反而比两个各验一条更难被"单形态退化实现"蒙过。
> 原计划表里 BC 场景的"按窗口"分支由 `Zone/HistAndFuture` 覆盖（两类同时成立 → 顺序取第 1 类）。

## 四、批量模式规模基线

`--all --year <YYYY>` 与 `diff` 全量遍历的规模基线**只用于"能跑完"的判据**，不作性能指标：

| 场景 | 规模 | 判据 |
|---|---|---|
| `windows --all --year 2026` | 本地树全部 zone | 跑完不抛异常；`summary.zones == 实际扫描数`；单 zone 错误进 `summary.errors` |
| `diff` 全量 | 两树 zone 并集 | 跑完；`changes` 按 zone 字节序；双跑逐字节一致 |
| 金标复算 | 5 版本 × 2 构建 | `bench/run.py --check` 退出 0；分母 > 0 |

**性能纪律**：纯 Python、单进程、无并行。若全量 diff 超时（> 60 s），**先查算法**（是否每次重读文件），
不许用"加缓存"掩盖重复 IO——缓存会让双跑确定性变复杂。

## 五、数据升级流程（版本从 2026e 往后走时）

1. `tools/fetch_tzdb.py --versions <new>` 下载 + 记录 provenance。
2. `bench/run.py --regen` 生成新金标（**只生成新增版本，不改旧版本**）。
3. `git status` 必须只显示新增文件 + 新增 pair 文件；**旧金标零改动**（否则说明复算逻辑变了，
   要单独一个提交说明原因）。
4. 更新 `data/README.md` §一.4 的"当前版本"行与 `plan/04` 本文的版本表。
5. 若新版本引入**新的解析形态**（如 TZif v5），先扩解析器 + fixture，再重生成。

## 六、不入仓清单（`.gitignore` 已封）

| 路径 | 理由 |
|---|---|
| `*.tar.gz` / `tzdata*.tar.gz` | 发布包体积大、可重新获取 |
| `data/_downloads/` | 下载缓存 |
| `bench/out/` | 基准中间产物 |
| `zones/` / `_private/` / `samples/` | 本地 zoneinfo 树 / 私有清单 |
| `*.csv` | 用户清单（fixture 用 `.json`/`.md` 承载） |

> `*.csv` 全封是**隐私红线**的落法：真实日志时间戳即生产数据。fixture 的清单用 `.json` 或 `.txt`
> （后者需 `.gitattributes` 明确 `-text` 若字节形态被测）。
